Dataset review · overview

suibench dataset — does each entry grade a model correctly?

The Move code and the labeled vulnerabilities are real and well-chosen. The issues sit in the grading layer — and several of them make a model that does good analysis score worse than one that does shallow analysis.

This page is the digestible overview. The full evidence is in DATASET_REVIEW.md; ready-to-apply fixes are in PROPOSED_FIXES/. Every finding survived an adversarial review that tried to refute it; the highest-impact ones were confirmed by running the exploits on a localnet.

The core defect, in one picture

How a correct finding is scored as a false positive

The benchmark credits an exploit to a bug by re-running it with the bug's gold patch applied: if the patch stops it, the label is credited. But several entries contain a second, unlabeled bug that the patch does not touch — so the exploit for it survives the patch, the attribution comes back empty, and the model is scored wrong.

Because the drain still succeeds under every gold patch, attribution is empty and the finding is bucketed as a false positive — even though the model found and exploited a real, more severe bug. Measured on-chain in 9 entries (systemic defect S1).

The eleven systemic defects

S1Unlabeled drain survives the gold patch

A correct, more-severe finding is scored a false positive. The single biggest source of mis-scoring.

execution-confirmed · 9 entries

S2Check satisfiable without the labeled bug

A path that never uses the labeled bug still passes, so a label is credited for the wrong reason.

execution-confirmed

S3Thresholds tuned to the reference exploit

Pass constants equal the shipped exploit's yield, not the ceiling a patched build allows — so larger correct exploits fail.

execution-confirmed

S4Single-label monoculture

All 32 confirmed entries carry one label, so attribution can never discriminate between competing bugs.

census-confirmed

S5Five entries mis-tiered as detect

They ship exploits and patches but no check.ts, so they are never execution-graded — and one aborts the whole patch run.

fixed · 4 oracles verified

S6Patch axis can't tell repair from deletion

A patch that just disables a function scores full credit when functional.ts never calls it.

confirmed

S7Decontamination leaks

The entry name, a compiler warning, and source comments leak the bug into the model-visible surface.

compiler-leak executed

S8Negative controls carry little signal

Only two, both distinguishable by a trivial grep and adversarial by construction — a thin false-positive base.

confirmed

S9Availability oracles ignore the abort reason

They pass on any non-success, so an unrelated abort is credited as the DoS.

confirmed

S10Label metadata: severity & harm

78% "critical" with exact-match scoring punishes a consistent responder; harm is unset on 45 of 48 labels.

census-confirmed

S11SOURCE.md drift

Nine provenance files describe a layout that no longer matches disk — the likely cause of the missing oracles.

confirmed

The larger design-level fixes — real accounting so the labeled bug is the only reachable one, thresholds derived from the patched ceiling, discriminative attribution — are written up per-entry in the report, left as proposals because they change grading semantics.

The five oracles, the patch-driver fix, and the localnet verification evidence. Nothing here modifies an existing file.
Method: a Move-semantics review of all 45 entries across eight dimensions — vulnerability reality, oracle soundness, patch narrowness, exploit validity, unlabeled defects, tier consistency, decontamination, and label quality. Every finding was attacked by an independent reviewer instructed to refute it; none was refuted, 19 were narrowed to a weaker accurate form. The nine highest-impact findings were confirmed by republishing each entry's base and gold-patched builds on a Sui localnet (sui CLI 1.69.2) and running the exploits. Localnet is not the pinned Docker image; pass/fail verdicts and measured gains are the load-bearing results.
